How it works / VERSION 6.0

Behind every chapter,
a shared way of working.

Follow the materials and decisions: how a chapter takes shape, how a review affects what comes next, and how a book keeps its own records as the system evolves.

01 / System roles

Creative judgment, execution,
and records each have a role.

The author sets the direction, reads, and decides. The AI assistant helps with research, drafting, and revision. Local tools connect preparation, checks, and saving; project files retain the work that has been adopted.

All commands use novel.py as their entry point. Model capabilities are separate from the local workflow. When switching to another assistant that works with local files, resume from the book's entry instructions and current state.

02 / Chapter cycle

What you have committed
sets up the next chapter.

Start a book by receiving existing materials, exploring direction and structure, and approving the initialization candidate. Drafting defaults to three chapters per batch; one at a time is also possible. The project can configure a batch limit of up to five. Every batch follows the same cycle.

Candidates · Room to try or discard

Dry runs use a copy of the project. Candidates that fail checks return for revision. The author can keep adjusting or retain the original draft.

Committed project · Adopted work becomes the reference

Approved changes enter the committed files after the final pre-save check. Exploratory drafts and unused plans do not automatically count as chapters, progress, or character facts.

Selected voice samples are also staged as candidates: INIT for initial setup, REVISE for an existing book. Complete the sample analysis and approve the same digest before updating the adopted sample. The two diagnostic passes cover reader engagement, then continuity and language. Each batch gets an independent review, with a full read at the end of an arc.

03 / Story reviews · 6.0

The outline guides the story.
The story reshapes the outline.

Reviews count chapters in their actual finalized reading order. Chapters three, six, and nine prompt a review of recent experience. Chapter twelve prompts a structural review, including the short review due then.

Use the existing outline and candidate workflow

Use INIT during setup and REVISE for an established book. Adopted changes enter the original outline and relevant chapter cards, then guide later writing. The allowed scope of chapter candidates remains unchanged.

Manuscript changes can invalidate review coverage

Records capture the chapter order and content digests covered. Changes to earlier chapters or their order prompt a recheck. Preparing a task, refreshing materials, or recording a deferral does not count as completing a review.

The program identifies pending work and records coverage. Waiting for the author does not count as a conversation; use replies already given in the current cycle. Explain local fixes separately from the judgment of the whole phase. The quality of reading, discussion, and research still needs to be checked.

04 / Approval and saving

The draft you approve
must still be the one you save.

The system computes a content digest for the candidate and records the relevant file baseline during the dry run. It checks again before saving, so an old approval cannot be reused after the draft changes.

If the candidate becomes version B, rerun the dry run and approve its new digest. If relevant committed files change, recheck against the current files, then rerun the dry run and obtain approval.

A content digest binds approval to specific content. It cannot tell whether the author actually read it or replace a review of character, language, and cause and effect.

05 / Learn from actual use

Keep the full record
of how a problem was handled.

The assistant records misunderstandings, rework, and workflow blocks using visible conversations and available evidence. Each record distinguishes what happened, how it was assessed, what was done, and how it was verified.

  1. 01 / Source

    Keep specific evidence

    Record conversation excerpts, tool results, or assistant observations, with their source locations and visible scope.

  2. 02 / Assessment

    Identify the kind of problem

    Distinguish creative choices, execution mistakes, template limitations, and program defects. Keep explanations that still need verification.

  3. 03 / Response

    Record the change and its scope

    Document the correction and affected steps, including reasons for leaving the system unchanged.

  4. 04 / Verification

    Make conclusions open to rechecking

    Unresolved issues enter the next preparation cycle. Check them against actual revisions and reading feedback. If an issue recurs, continue under the same ID and preserve its history.

↳ Book issue records → Reusable lessons → Assess system changes → Verify in later use

Included in records and backups

Execution issues are kept in an append-only log for the book and included in backups. This does not change the creative commit HEAD or put the entire log into every chapter's reading package.

Clear evidence scope; book data stays with the book

The system does not automatically collect all chats or other tasks. The assistant records evidence it has actually seen. Updates to the template extract only reusable methods and rules.

06 / Separate books and ongoing updates

The system can evolve.
Each book keeps what it has built.

Use the downloaded folder for one book. You can also save an unused template before writing and duplicate it for future books, or download again. Keep the existing folder for your current book. Tool updates first check the installation baseline and local differences.

How do you recover after an interrupted save?

The full write has not yet been verified

The system preserves the unfinished transaction and pauses further writes. Inspect the files involved and explicitly run recovery to return to the pre-save state according to the records.

Verification passed; the commit is being finalized

Complete commit records and history updates according to where the interruption occurred, retaining the verified content. Viewing status alone does not trigger recovery.

Caught write errors trigger an attempt to roll back. Recovery after a forced interruption must be explicitly run; check the relevant records first.

Retained candidates · Preserve the commit scene

After a successful chapter commit, the candidate is moved atomically into retained storage and its location is reported. Material saved during the commit can still be checked there. It does not automatically become committed text or an approved candidate for the next commit.

Regular backups · Currently effective content

Candidates, retained candidates, reading packages, and transaction history are excluded. Save unused material separately if you need to keep it. Snapshots of interrupted transactions are labeled separately; they do not guarantee consistency or replace the original project's transaction recovery records.

6.0 keeps schema 2 and the existing INIT / REVISE workflows. New books default to General mode, focusing on reader expectations and development over a phase. Opponents and advancement are required only in Progression and Conflict mode. Older cards without a mode field retain their original interpretation; books without an active engine are not forced to add cards. An upgrade does not restart an existing book or automatically adopt new story plans.

07 / Limits of judgment

A workflow can be checked.
A story still needs to be read.

Technical safeguards improve the reliability of files, versions, and records. The life of a book must still be judged from its actual passages and the reading experience.

Program checks

  • Required materials, file structure, and records are present
  • The candidate digest matches the approved content
  • Relevant baselines, transactions, or review coverage have changed
  • Synchronization touches local differences

Author, AI, and reader judgment

  • Character motives and cause and effect are believable
  • Voice, scenes, and narration suit the book
  • Pacing and expectations give reasons to keep reading
  • Research and revisions actually improve the work

Passing software verification only confirms the corresponding workflow checks. Literary quality and long-term writing benefits need manuscript review, real feedback, and continued use to assess.
